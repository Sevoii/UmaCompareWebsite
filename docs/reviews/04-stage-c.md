# Stage C review

1. **High — `optimizer.js:372-408,464-467`: Stop during team loading does not stop the run.** Before `running.pool` exists, Stop only sets `signal.aborted`; after the fetches resolve, the code still creates and initializes workers and starts `runOptimization`, whose loop does not check that signal before its first evaluation. A user can press Stop while “Loading teams...” is shown and still trigger a full generation. **Fix:** check the signal after each await and before worker creation, initialization and every generation; use an AbortController for fetches where possible. Test Stop during each loading phase.

2. **High — `optimizer.js:95-115,383-393`: race/snapshot state can change while a run is being prepared.** Race controls remain enabled, and `refreshSnapshot` assigns the global `snapshot` before awaiting data; `optimize` captures the old race and prior but reads `snapshot.snapshotId` again after asynchronous work. Changing the race during loading can combine the old race and usage data with a new snapshot's teams and label. **Fix:** freeze a validated run configuration including snapshot and snapshotData before any await, or disable all relevant controls during preparation and execution; guard stale refreshes before committing globals. Test a delayed fetch while changing race.

3. **Medium — `optimizer.js:113-128,162`: Optimize can be enabled for an invalid or stale snapshot.** A successful refresh sets `optimizeButton.disabled = running !== null` without checking whether an uma exists. Conversely, a failed refresh leaves the previous `snapshotData` in place; selecting or editing an uma invokes `updateOptimizeEnabled`, enabling Optimize with stale data for the new race. **Fix:** clear snapshot/data while loading or on failure, and centralize button state in one function that also checks the current refresh token, selected uma, and loading/error state. Test initial load without an uma and a failed race change followed by editing the uma.

4. **Medium — `optimizer.js:269-277,342-347,319-324`: live build actions are displayed before they work.** During optimization the “Best so far” card includes Save and Export buttons, but `lastRun` remains null until the entire search ends, so clicking either silently does nothing. **Fix:** hide or disable these actions until final results exist, or maintain a current result/runner mapping as each generation completes.

5. **Medium — `optimizer-run.js:67-78,107-120`: a failed worker is not retired and in-flight jobs continue after a run error.** `Promise.all` rejects on the first worker error while other lanes are still running; unless the caller immediately terminates the entire pool, those lanes can continue posting results or pick up more chunks, and a subsequent `run` can overlap them. **Fix:** make a failed run terminate or cancel the pool and await lane settlement before returning; reject future calls on a failed pool. Add a multi-worker error test with another delayed lane.

6. **Low — `optimizer.js:348-349,448`: only four runner-ups are shown.** The final array is truncated to five total entries and then sliced from index 1, while the spec asks for the best plus the top five runner-ups. **Fix:** retain and render six entries when available, and test the displayed count.

`node --test tests/` passed all 49 tests. The common-trial generation loop, paired comparison direction, prior-best retention, and budget use were consistent with the reviewed spec by inspection. No issue was identified in the nav link or appended styles.

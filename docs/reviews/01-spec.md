# Skill optimizer implementation review

1. **Critical — `tools/gen-skill-data.mjs:123`, `skill-data.js:8`, and `docs/SKILL_OPTIMIZER_SPEC.md:79-83`: `is_basis_distance` is encoded backwards.** The engine computes `v = min(course.distance % 400, 1)` and accepts `is_basis_distance == flag` only when `v != flag` (`GlobalSim/src/activation_conditions.rs:714-720`). Thus a basis distance has engine condition value **1**, but its direct computed value is 0; the current documentation says to pass 1 when `distance % 400 === 0` without describing the inversion. An implementation that evaluates the emitted term directly will reject e.g. `200131` on 1600 m and admit it on non-basis distances. **Fix:** document the condition's effective value explicitly as `Number(distance % 400 === 0)` (or normalize this one key in the generator to that semantic value), and add tests for both `is_basis_distance == 1` and `== 0`.

2. **Critical — `docs/SKILL_OPTIMIZER_SPEC.md:94-97`: teammate replacement cannot identify the requested slot from the stated member field.** Hakuraku members use `racingStyle`, not `style` (`hakuraku-import.js:15,75`), and style 6 is explicitly a Debuffer *role*, not a runner style. Consequently `member.style === 6` is never a valid way to replace a Debuffer slot; all such teams will be skipped. Matching by running style is also ambiguous for duplicate styles and does not identify the API archetype slot. **Fix:** establish and test the `/teams?slots=` response ordering/slot metadata, then remove the member by that returned slot index. Carry the requested slot index through pre-conversion and splice the candidate at the same index. If the API does not guarantee order, fetch or retain an explicit slot-to-member mapping; do not infer it from a style.

3. **High — `docs/SKILL_OPTIMIZER_SPEC.md:76-86,132-134`: the tier representation is contradictory and does not define an eligible catalog.** The rule says builds list only an upper tier and a gold includes its white, which requires excluding every ID referenced by `lower` (including circle whites). But eligibility as written includes all non-negative records, so both `200531` (gold) and `200532` (white) qualify. The mutation rule then requires a white-to-gold/gold-to-white transformation even though whites are said never to be listed. This can produce duplicate alternatives, wrong costs, and undefined mutation behavior. **Fix:** choose and state one representation. For the requested “upper-tier only” model, derive `lowerIds = new Set(Object.values(SKILL_DATA).flatMap(x => x.lower ? [x.lower] : []))`, exclude `lowerIds` from eligibility/prior/sampling, retain the summed discounted cost on the upper ID, and remove/replace the tier-change mutation. If whites must be selectable, represent them as first-class builds with their own cost and list them in the output instead.

4. **High — `docs/SKILL_OPTIMIZER_SPEC.md:42-43,84-86`: discounting must be defined as a per-component calculation, not a total-cost calculation.** The text says the discount applies to both tiers, but it does not give the unambiguous formula. `round((goldNeed + whiteNeed) * (1-d))` differs from `round(goldNeed * (1-d)) + round(whiteNeed * (1-d))`, which affects budget feasibility and all search invariants. **Fix:** define a single helper, e.g. `discountedNeed(id) = Math.round(need * (1 - discountPct / 100))`; `skillCost(id) = discountedNeed(id) + (lower ? discountedNeed(lower) : 0)`, and use it everywhere (prior, sampling, mutation, UI, export tests).

5. **High — `docs/SKILL_OPTIMIZER_SPEC.md:108-110`: runner construction unconditionally inserts an invalid unique when the costume has none.** The inputs correctly qualify the unique with “if `isSkill`” (line 38), but the worker JSON example always begins its skills array with `{unique, ...}`. Some costumes will have no catalog skill, so this can send `undefined`/an invalid ID to GlobalSim and fail an entire worker batch. **Fix:** build `const skills = [...(isSkill(unique) ? [{ skillId: String(unique), level: uniqueLevel, isUnique: true }] : []), ...bought]`; ensure the own-unique eligibility exclusion uses the same normalized string ID.

6. **Medium — `tools/gen-skill-data.mjs:27-31,76` and `docs/SKILL_OPTIMIZER_SPEC.md:76-83`: the advertised “static” eligibility filter omits conditions that are wholly determined by the course.** `is_dirtgrade` and `is_tight_track` are immediate course/race checks in GlobalSim (`activation_conditions.rs:734-752`), yet neither is in `STATIC_KEYS`. The generated catalog consequently marks buyable course skills such as `202241` and `202251` as unrestricted. This is a false-positive eligibility/prior issue, not merely a proc-rate detail. **Fix:** either add supported encodings/evaluators for these two keys (including GlobalSim's dirt-grade track-ID rule), or explicitly document the filter as deliberately conservative and do not describe eligibility as “possible”; add regression tests for a tight and non-tight course and a dirt-grade and non-dirt-grade course.

7. **Medium — `docs/SKILL_OPTIMIZER_SPEC.md:87-90`: the prior is incoherent with the static running-style normalization.** Eligibility correctly uses base Front (1) for Runaway because engine `running_style` matches Nige/Oonige (`GlobalSim/src/horse_types.rs:101-104`), but the prior instead uses only `uma-usage.style === 5`. That yields a tiny or missing prior for Runaway while excluding the much more relevant Front usage. **Fix:** state whether the product intentionally wants an Oonige-only empirical prior. Otherwise aggregate styles 1 and 5 for a Runaway and divide by the matching combined `summary.styles` owner count; keep the displayed numerator/denominator aligned with the sampling weight.

8. **Medium — `docs/SKILL_OPTIMIZER_SPEC.md:98-101,138-141`: common-random-number and stopping comparisons are underspecified across generations.** Candidates share trials *within* one generation, but each generation draws new trials. “The previous generation's best” must therefore be explicitly re-evaluated on the current trial list before its paired CI is computed; otherwise the vectors are not paired. The score direction is also only implicit. **Fix:** retain the prior generation's winning build, add it to every next-generation evaluation (even if it would not otherwise be an elite), compute `current - previous` per trial, and define significance as CI upper bound `< 0` for place and lower bound `> 0` for either win rate. Specify whether the final winner is the best on its last-generation trials or is re-evaluated on a final common holdout.

9. **Medium — `docs/SKILL_OPTIMIZER_SPEC.md:119-135`: “distinct population” may be impossible and has no bounded fallback.** With a small SP budget, restrictive course, or one remaining group, there may be fewer valid canonical builds than `population`; repeated retries can loop forever. The 40 failed-draw cutoff does not solve duplicate generation. **Fix:** bound attempts per offspring, calculate/track the reachable unique count where practical, then return a smaller population with a visible warning (or permit duplicates but evaluate each canonical build once). Make the stop/elite math robust to actual population size.

10. **Medium — `docs/SKILL_OPTIMIZER_SPEC.md:51,59-72`: the selected race, live Hakuraku snapshot, and local opponent pool can describe different Champions Meetings.** The UI permits any pool while the snapshot is selected from the current CM/custom race, producing a field and prior from one meeting against opponents tuned for another. **Fix:** automatically select/filter pools whose `cm` matches the preset meeting, require an explicit “allow mismatched pool” confirmation for exceptions, and label the final result with all three data sources.

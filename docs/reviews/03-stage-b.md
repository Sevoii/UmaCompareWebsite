# Stage B review

1. **High — `optimizer-worker.js:13-15` and `optimizer-eval.js:16`: worker initialization uses a different field from the specified protocol.** The spec sends `init { race, pool, teammateTeams, slot }`, but the worker reads `teammates`. A page following the spec initializes successfully, then every run fails when `evaluateTrial` indexes `undefined`. **Fix:** choose one field name in the spec, worker, and caller; validate the context during init and add a worker-level test using the documented message.

2. **Medium — `optimizer-worker.js:18-20`: a full chunk produces no progress until all its races finish.** With 64 candidates and a 200-trial generation split over a few workers, each worker can spend thousands of simulations before sending a message. The specified live races-done progress remains frozen, and stopping loses all work from in-flight chunks. **Fix:** emit incremental progress (and, if results so far must survive Stop, completed trial results) after each trial or small batch; include a batch identifier and trial index so the caller can merge results in original order.

3. **Medium — `optimizer-data.js:79-87` and `optimizer-eval.js:17-21`: teammate removal loses the original member position.** For the supplied fixture's `[style 2, style 6, style 1]` team, selecting archetype slot 2 (style 2) removes index 0 but inserts the candidate at index 1; the surviving members shift relative to their original gates. This follows the literal slot-index rule, but does not replace the selected member in place, and changes the field's gate assignment depending on the API's member ordering. **Fix:** define which ordering is intended. If replacement should preserve the sampled team, retain each removed member's index with the pair and use it for insertion and scoring; add a test where the matching member index differs from the archetype slot index. If fixed archetype slot placement is intentional, document the resulting gate reassignment explicitly.

4. **Medium — `optimizer-worker.js:10-25`: errors lack request identity and initialization failure leaves a usable-looking context.** Multiple queued runs receive indistinguishable `done`/`error` replies, and `context` is assigned before `init()` succeeds. An initialization failure followed by a queued run can yield a second unrelated error or use an uninitialized engine, making it difficult for the page to reject the right pending job and terminate cleanly. **Fix:** validate and commit context only after successful initialization, include request IDs in every response, reject runs before ready, and test init failure and multiple queued batches in a worker harness.

5. **Low — `optimizer-eval.js:35-38`: empty teammate pools and undersized opponent pools are not validated.** If all fetched teams are skipped, `teammateCount` is zero and trials still contain index 0; evaluation then fails while spreading an undefined pair. A pool with fewer than two teams likewise cannot provide the requested distinct opponents. **Fix:** validate these counts before drawing trials and return a clear actionable error; test both cases.

The stage A changes address the reviewed examples: recursive component cost and chain-aware crossover handle the tested three-tier chain, base-stat keys are omitted from generated static options, greedy fill filters unaffordable candidates, and distribution updates normalize. These checks confirm the stated changes, not the correctness of every inferred upgrade relationship. The earlier review's claim that Hakuraku members lack a `style` role field was incorrect; the supplied fixture includes both `style` and `racingStyle`.

`node --test tests/` passed all 32 tests. The real-race test covers evaluation, but the suite does not exercise the browser worker protocol or concurrent worker progress.

# Stage A review

1. **High — `optimizer-core.js:112` and `optimizer-core.js:114`: static stat conditions use raw input instead of the engine's adjusted base stats.** GlobalSim builds `HorseParameters` with `ranked_base_stat` including mood and the >1200 adjustment (`GlobalSim/src/race_solver_builder.rs:248,278-285`); `base_power` reads that adjusted value (`activation_conditions.rs:1233`). For example, at Great mood raw power 1160 exceeds 1200 after the mood multiplier, but the optimizer rejects dirt skill `202332`, whose options require `base_power >= 1000` with a split at 1200 (and other thresholds can exclude skills outright). **Fix:** derive the same engine base values using the actual mood and team rank, or conservatively leave stat predicates unknown until that transformation is available. Add threshold tests against the engine.

2. **High — `optimizer-core.js:53` and `tools/gen-skill-data.mjs:104-106`: generated gold prerequisites can be the negative skill.** `200014` (Right-Handed Demon) is generated with `lower: 200013` (Right-Handed ×), so `skillCost(200014)` charges 130 + 50 instead of the corresponding positive prerequisite. The same pattern occurs for `200064` and other green golds. Builds can consequently fit an incorrect SP budget. **Fix:** derive prerequisites from authoritative upgrade relationships rather than adjacent IDs, regenerate the data, and test gold/circle variants with negative siblings. Also check the multi-tier `202341`/`202342`/`202343` group rather than assuming one lower edge.

3. **Medium — `optimizer-core.js:419` and `optimizer-core.js:360`: distribution weights are not normalized after updating, but crossover treats them as probabilities.** Elite frequencies sum to the average build size rather than 1, so repeated updates increase the sum of `p`; the removal formula `1 / (0.05 + activationRate * p)` changes scale across generations even when relative sampling probabilities do not. **Fix:** normalize elite frequencies and the updated distribution (including the floor) to sum to 1 before both sampling and crossover; test multiple generations and the removal weights.

4. **Medium — `optimizer-core.js:185`: Runaway prior contradicts the specified user rule.** The spec explicitly sets `s = 5` for Runaway, but `priorStyles` adds style 1 counts and owners. For a Runaway-only sample of 30 and Front sample of 100, the implementation weights the skill as 135 instead of 35, changing the search. **Fix:** follow the stated style-5 rule, or obtain a spec decision and update it and its denominator consistently. My earlier review suggested aggregation; that suggestion was a product choice, not evidence that the explicit rule was incorrect.

5. **Medium — `optimizer-core.js:275`: greedy fill can stop with affordable skills remaining.** After 40 expensive draws it stops even though a cheap skill remains in the without-replacement pool. With 40 high-weight skills costing more than the remaining budget and one low-weight affordable skill, the returned build is not maximally filled, contrary to the test requirement in the spec. **Fix:** filter out unaffordable candidates and continue until no eligible group fits, or remove the miss cutoff for this finite pool. Test an adversarial weighted pool.

6. **Medium — `optimizer-core.js:154` and `tests/optimizer-core.test.mjs`: tier policy remains unresolved.** The implementation permits white-only builds and tests them as first-class, while the earlier review interpreted “builds list only the upper tier” as excluding lower IDs. The spec also explicitly describes white-to-gold mutation, supporting the implementation's interpretation that a white may be bought alone. **Fix:** clarify that only a purchased upgrade suppresses its lower ID in that build; retain white-only builds if intended, and test that gold and its white never coexist. My earlier review's proposed blanket exclusion of lower IDs was too broad.

The earlier review's first finding was also incorrect: the documented effective `is_basis_distance` value and `raceContext` implementation are consistent with the engine's inverted comparison; the 1600 m regression test passes.

`node --test tests/` passed all 20 tests outside the sandbox; the sandboxed run could not spawn the test subprocess (`EPERM`). No behavior difference was identified in the race-controls extraction or `runTrial` export by inspection.
